# 06 预训练数据：学习分布首先由数据管道决定

上一章解释了如何让一次推理更便宜；这一章问训练时应该把算力花在哪些文本上。
对应公开课程地图 W6 与 HW3。课程地图来自个人整理，教材另参见课程团队 [AML-LLM](https://github.com/dujh22/AML-LLM)。
本章原创组织原理与实验方案，不把课程地图仓库中的个人实验数字当作本项目结果。

## 6.1 从三个具体场景开始

**场景一：网页转载。** 你获得一万篇网页，其中同一篇教程转载了三千次。
训练一个 epoch 并不代表学过一万个独立知识单元；转载会让这篇教程获得非常大的梯度权重。
若转载版分别进入训练和验证，低验证损失还可能来自记忆，而不是对新文本的预测能力。

**场景二：代码与散文混合。** 代码能提供结构化模式，但训练中增加代码比例可能减少中文散文的更新次数。
有限 token 预算下，数据配比是在分配学习机会。不存在脱离目标分布的绝对最佳配比。
质量分数高的英文资料也不能自动代表中文任务、方言或短对话的质量。

**场景三：抓取到论文的测试题。** 网页可能包含 MATH、GSM8K 的题目与解答。
即使文件名叫 `train`，它也可能污染后续 benchmark。
去重和去污染因此是不同工作：前者减少重复权重，后者保护评价问题的独立性。

学完本章，应能解释数据混合的概率意义，画出可追溯管道，区分本仓库的精确去重与生产级近重复处理。

## 6.2 数据质量为何不是一个单独的分数

语言模型最小化目标分布上的负对数似然：

$$
\mathcal L(\theta;q)=\mathbb E_{z\sim q}
\left[-\sum_{t=1}^{|z|}\log p_\theta(z_t\mid z_{<t})\right].
$$

这里 $z$ 是 token 序列，$\theta$ 是参数，$q$ 是管道处理后的采样分布。
若实现用 token 总数归一，长文档贡献更多 token；若先对每文档平均，再对文档平均，短文档的相对权重会上升。
同一份文本集合采用不同采样器，也会定义不同的训练分布。

对于 $K$ 个数据源，可写成 $q(z)=\sum_{k=1}^{K}w_kq_k(z)$，其中 $w_k\geq0$ 且 $\sum_kw_k=1$。
$w_k$ 应说明按文档、字节还是 token 定义。三者通常不相同。
例如按文档各采一半短对话和长论文，实际 token 大部分可能仍来自论文。

“质量”至少涉及可读性、任务相关性、正确性、覆盖度和使用条件。
一个文本有完美语法，却可能包含虚假事实；一个论坛回复有拼写错误，却可能包含稀有而正确的故障诊断。
过滤器是代理指标，不能把其输出叫作真实知识质量。

## 6.3 原始记录、内容记录与训练记录

将三个层次分开，可避免清洗后找不到证据来源。

| 层次 | 应保存的信息 | 不应混淆的量 |
| --- | --- | --- |
| 原始记录 | 来源 URL、抓取时间、响应/文件摘要、原始 split、许可信息 | 网页数量不等于可用文档数 |
| 内容记录 | 提取文本、语言、过滤原因、重复簇、规范化摘要 | 字符数不等于 token 数 |
| 训练记录 | tokenizer 版本、token 数、分片、混合权重、EOS 规则 | 训练曝光量不等于独立 token 数 |

正文常用 JSONL：每行一个 JSON 对象，至少有字符串 `text`。
`id`、`source`、`split`、`license` 等字段应由上游保留；本仓库最小管道不代替完整 provenance 数据库。
不要把来源 URL 写进每篇训练正文，除非你的任务有意学习引用形式。
删除元数据与保存元数据不是矛盾：训练载荷与审计清单可以是两个文件。

## 6.4 管道的顺序会改变结果

建议顺序如下，每一步记录输入、输出与剔除原因的数量：

1. 登记来源与使用条件，确认原始公开 split。
2. 从 HTML/PDF 等载体提取正文，保留原始记录摘要。
3. 进行 Unicode 与空白规范化，检测空文本和损坏文本。
4. 执行语言、长度、结构与质量规则，抽样检查误杀。
5. 在整个待切分集合上精确去重；扩展实验再做近重复聚类。
6. 检查 benchmark 重叠；按来源官方 split 或重复簇划分数据。
7. 只使用训练文本学习 tokenizer；冻结后编码验证与测试。
8. 插入文档结束标记、分片、打乱，并保存数据 manifest。

去重在随机切分之后进行，会留下“训练一份、验证一份”的重复。
对跨 split 的官方数据发现重复时，应记录并采用明确规则，例如从训练侧移除重叠，保留官方评价侧。
不要把官方 test 重新随机拆成自己的训练数据。

规范化也有代价：把连续空格全部压成一个空格可能破坏 Python 缩进。
做自然语言处理的规则应经过代码样本审计，不能对所有模态盲目套用。
内容规范化规则变更后，摘要、去重结果和稳定划分也可能变化，应升级数据版本。

## 6.5 精确去重、近重复与污染检查

精确去重可对规范化文本取稳定摘要，保留一个代表文档。
它能识别完全相同的正文，不能识别换标题、改标点、删一段后的转载。
近重复常将文档变成 $n$-gram 集合 $S_a,S_b$，比较 Jaccard：

$$J(a,b)=\frac{|S_a\cap S_b|}{|S_a\cup S_b|}.$$

MinHash/LSH 是寻找候选相似文档的近似方法，不是“语义相同”的证明。
短文档的相似度不稳定；模板页共享导航词也可能触发误判。
应检查重复簇大小分布，并人工看若干最大簇与阈值附近的簇。

对 benchmark，匹配应覆盖题目和答案片段，报告采用字符还是 token $n$-gram。
仅检查 URL 名称无法发现嵌入网页的题解；仅匹配答案数字又会误伤大量正常文本。
检查结果为零也不证明完整无污染，可能受提取失败、改写或上游未知数据影响。

[DCLM](https://github.com/mlfoundations/dclm) 的官方管道区分 Ray 过滤、Rust 模糊去重、tokenize/shuffle、训练与评测。
这提供了工程阅读路线，但本仓库 `prepare_jsonl` 只实现小规模精确去重，不宣称复现 DCLM-Baseline。

## 6.6 数据划分与稳定哈希

本仓库 [`data.py`](../src/fm_tutorial/data.py) 提供：

```python
prepare_jsonl(input_path, output_dir,
              min_chars=80, val_fraction=0.1, text_field="text",
              validation_input=None)
```

它读取真实 JSONL、规范化并全局精确去重，随后用稳定摘要划分，输出 `train.jsonl`、`val.jsonl` 和报告。
稳定哈希意味着相同规则下，同一文本不会因为输入顺序变化而换 split。
`val_fraction` 是分配阈值；有限数据的实际比例不保证精确等于该数值。
它没有 HTML 提取、来源许可判定、近重复聚类或 benchmark 污染检测功能。

若使用 WikiText 等有官方 split 的数据，应提供 `validation_input`，不能把 test 合并进随机划分入口。
此模式保留原始成员方向，但当前实现会删除与训练重叠的验证文档；processed val 是处理后的开发集，不等于完整官方评价集。
若最终评价要保持官方 validation/test 不变，应独立保存原始评价集，并从训练侧移除重叠后交给可信评测流程。
若只做来源不带 split 的真实语料实验，则可采用哈希切分。

```bash
python scripts/prepare_data.py --input data/raw/train.jsonl \
  --validation-input data/raw/validation.jsonl --out-dir data/clean
python scripts/train_tokenizer.py --data-dir data/clean \
  --out-dir data/processed --vocab-size 2048
```

上述输入必须是实际取得的源文本；不要用手写三句文本填充训练集以宣称完成预训练。
数据卡中检查：处理后独立文档数、训练/验证交集、字符长度分布、每源留存率。

## 6.7 Tokenizer 与 packing 也是数据决策

本仓库 [`ByteBPETokenizer`](../src/fm_tutorial/tokenizer.py) 使用字节 0–255、EOS=256、PAD=257，合并 token 从 258 起。
训练 tokenizer 只读训练文本；验证文本只经过冻结后的 `.encode()`。
同一模型的 tokenizer 文件、词表大小与特殊 token ID 必须一致。
不能在训练中途扩词表，却仍载入旧 embedding 并比较困惑度。

`train.bin`、`val.bin` 是 uint32 token 流，每篇文档末尾添加 EOS。
EOS 是结束信号，不是注意力隔离墙。
简单连续流切块会允许后一篇文档关注前一篇文档；这是一种训练选择，不等于分文档 attention mask。
若要文档隔离，应增加 segment mask，并在训练和验证中同时采用相同规则。

对输入 $X\in\mathbb N^{B\times T}$，模型 logits 为 $Z\in\mathbb R^{B\times T\times V}$。
next-token 训练用 `Z[:, :-1]` 预测 `X[:, 1:]`。
PAD 位置不参与损失，因果遮罩只防止看未来，两种遮罩解决不同问题。
截掉最后一个预测位置后，实际计入损失的 token 数必须按 mask 计数，而不是简单写 $BT$。

## 6.8 两个官方项目应该怎样读

[The Pile](https://github.com/EleutherAI/the-pile) 是多来源语言建模数据集的复现代码入口。
它的组件表展示了不同来源权重与多次曝光；这些权重是该项目的选择，不能直接成为你的最佳配比。
该代码仓库不是“所有组件均可任意使用”的统一授权书；数据组件的使用条件应分别确认。

DCLM 更适合学习受控数据实验：固定规模和训练配方，改变数据处理，再使用官方评测套件。
其 README 记录了 2025-09 对 CORE/EXTENDED 基线计算的修正。
比较时须写清 eval commit 和 `v1`/`v2`，不能混合旧报告与新汇总分数。
本教材没有执行其大规模训练，没有把官方硬件和成本表当作本项目实测。

## 6.9 使用真实数据的实验设计

先用 [WikiText-103 raw](https://huggingface.co/datasets/Salesforce/wikitext) 官方训练文本验证完整链路。
WikiText 是现有公开语言建模数据集；保留来源 split，并将连续行恢复为一致的文档单位。
若逐行处理，`min_chars=80` 会删除标题和短句，实际上改变了数据分布，应报告这一点。

选择三个处理条件：最小规范化、加入精确去重、再加入一种明确定义的过滤规则。
固定模型、tokenizer、优化器、有效 batch、训练 token 预算和评价集，使用相同随机种子集合。
tokenizer 可从共同训练池训练一次后冻结，避免把词表差异混入清洗效果。
过滤导致 token 不足时，缩小所有条件预算，或明确报告重复曝光；不悄悄补齐伪文本。

| 测量 | 目的 | 必须记录 |
| --- | --- | --- |
| held-out token NLL | 检查语言建模分布 | 同 tokenizer、同 mask、同文档规则 |
| 处理吞吐与峰值内存 | 检查管道成本 | 主机、版本、输入/输出字节量 |
| 留存率与重复簇 | 解释分布改变 | 分来源、分长度，而非仅总比例 |
| 官方任务得分 | 检查下游迁移 | 可信 harness 的 commit、任务配置、样本输出 |

小模型 NLL 变化不等于通用能力提升；跨域结论需要相应官方 benchmark。
更大资源下可采用 DCLM 的正式规模与评测协议，但更换训练器后应称为独立实验，不能直接报官方赛道排名。

## 6.10 交付与思考

交付原始来源清单、数据卡、逐阶段统计、重复与污染审计、冻结 manifest，以及真实训练日志。
报告不填预期提升，也不把调试测试样例称为 benchmark。相关完整作业见 [作业 03](../assignments/03-data-scaling.md)。

1. 同样的独立文档数，为何训练 token 曝光量仍可能相差十倍？
2. 若过滤后验证损失下降，但中文任务退步，应该检查哪一类留存率？
3. 一篇长论文与十篇短问答，在 token 平均与文档平均下各占多少权重？
4. 如何证明自己的去重实现有效，又说明它仍不能保证无污染？
