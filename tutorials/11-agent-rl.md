# 11 · 从回答正确到行动成功：Agent 强化学习

一名代码助手看到“修复时区导致的日期错误”，给出看似合理的补丁，却没有安装依赖、运行测试或检查回归。
回答文本的质量与任务完成率在这里分开了。
要训练能够反复观察、选择工具、修正错误并终止的模型，训练样本必须包含环境反馈，奖励也必须来自任务结果。
本章解释这一步为何改变了优化问题，以及怎样让训练信号真正对应行动能力。

学习后应能写清一个任务的状态、观测、动作、终止与奖励；辨认信用分配和奖励漏洞；审查一条轨迹的训练掩码。
阅读时把“能运行一次工具循环”“能在公开基准完成任务”“经过长程 RL 训练”视为三种独立证据。
本仓库提供的是第一种基础设施及损失函数教学部件，未执行真实长程 Agent RL 训练。

## 11.1 环境进入概率模型

普通语言模型建模的是文本序列条件概率。
Agent 则在动作后获得新观测：点击按钮会改变页面，编辑文件会改变代码库，执行命令会产生退出码。
这些变化由环境决定，不是语言模型自己生成一句“操作成功”就能完成。

令隐藏环境状态为 $s_t$，观测为 $o_t$，模型动作是 $a_t$。
环境转移核 $P(s_{t+1}\mid s_t,a_t)$ 描述动作如何改变世界；观测核 $O(o_t\mid s_t)$ 描述模型能看到什么。
浏览器只展示当前 DOM 或截图，通常无法一次看到全部数据库状态，所以很多任务更适合用部分可观测决策过程描述。
策略应条件于历史 $h_t=(o_0,a_0,o_1,\ldots,o_t)$，或由历史构造的记忆状态，而不是假定当前截图包含一切。

一条轨迹记为 $\tau=(o_0,a_0,r_0,\ldots,o_T)$。
在环境和初始任务分布固定时：

$$
p_\theta(\tau)=p(o_0)\prod_{t=0}^{T-1}\pi_\theta(a_t\mid h_t)P(o_{t+1},r_t\mid h_t,a_t).
$$

这里的第二个因子把隐藏状态积分掉了，是对可观测历史的环境分布简写。
工具返回的文本影响下一步决策，但不是策略的随机动作，因此不能把工具输出 token 当成模型动作求策略梯度。
如果模型输出一个 JSON 工具调用，动作概率是这一段由模型生成的 token 的条件概率乘积。

## 11.2 三个任务，三种可验证结果

**代码修复。** 输入是仓库和 issue；动作包括检索、编辑和测试；结果由隔离环境里的测试判定。
开发期测试的通过可以帮助定位问题，但最终评测应使用冻结的独立验收流程。
[SWE-bench](https://github.com/SWE-bench/SWE-bench/blob/main/README.md) 评测真实 GitHub issue 对应补丁；Verified 是经人工检查的一个特定子集，不是“任何补丁都已被证明可靠”。

**网页工作流。** 输入要求把某条记录改到指定状态；观测是页面；动作是导航、点击、输入。
成功应检查应用最终状态，而不是检查回答里有没有“已完成”。
[WebArena](https://github.com/web-arena-x/webarena) 提供自托管网站任务；[BrowserGym](https://github.com/ServiceNow/BrowserGym/blob/main/README.md) 是统一浏览器环境接口及基准适配生态。
它们的环境版本、重置方式和任务编号必须同时记录。

**生存与制作。** 获得物品可能先要探索、收集、加工，稀疏末端奖励让早期动作的价值很难识别。
[MineRL](https://github.com/minerllabs/minerl/blob/dev/README.md) 提供 Minecraft 相关环境和数据，是理解长时序控制的公开入口。
它的观测、动作空间、环境依赖与网页任务不同，不能拿一个任务的成功率解释另一种能力。

这三个场景的共同点是外部状态变化；差异在于可观测性、重置成本、动作时长和验证强度。
选择算法前先回答这些问题，比直接把聊天 RL 配方搬到工具调用上更有效。

## 11.3 回报与信用分配

目标通常写为最大化期望折扣回报：

$$
J(\theta)=\mathbb E_{\tau\sim\pi_\theta}\left[\sum_{t=0}^{T-1}\gamma^t r_t\right],\qquad 0\leq\gamma\leq1.
$$

有限且必须完成的任务可以使用 $\gamma=1$，再显式施加 token、动作或时间成本。
若每个动作耗时差别很大，以动作次数折扣与以真实时间折扣不是同一个目标。
例如安装依赖耗时较长但可能是必要步骤，惩罚所有长动作会误导策略跳过准备。

对只在终点获得成功奖励的任务，回报无法直接解释哪一次检索起作用。
REINFORCE 的一种形式是：

$$
\nabla_\theta J=\mathbb E\left[\sum_t\gamma^t\nabla_\theta\log\pi_\theta(a_t\mid h_t)\bigl(G_t-b(h_t)\bigr)\right],
\quad G_t=\sum_{k=t}^{T-1}\gamma^{k-t}r_k.
$$

这里 $G_t$ 从当前步重新开始计折扣，因此对应初始时刻的 $J$ 时还需外层 $\gamma^t$。
若把折扣吸收入访问分布，或定义另一种平均回报目标，应同时改写采样与公式约定，不能直接漏掉该因子。
基线 $b(h_t)$ 降低方差；它不能使用当前动作的随机性来任意消除该动作的真实贡献。
有价值模型时可用优势估计，但价值模型也会在长轨迹、不稳定工具和新任务上失准。
无价值模型的组相对方法可以用同一个初始任务的多条轨迹形成相对奖励。
在只有终端奖励且忽略中间折扣的教学近似中：

$$
A_i=\frac{R_i-\bar R}{\sqrt{\frac1K\sum_j(R_j-\bar R)^2}+\epsilon}.
$$

组里所有轨迹都失败时，没有组内排序信息；标准化不能凭空创造监督。
必须报告有效奖励方差的组比例，并考虑课程学习、示范初始化或更易获得反馈的训练任务。
当所有轨迹都成功时也存在同样问题，任务难度应该覆盖模型可改进的区间。

## 11.4 奖励应承认边界

“测试通过”为代码任务提供较强信号，但测试只覆盖其断言。
如果策略能编辑测试、读取答案、破坏评测器或缓存旧结果，就可能提高奖励而没有修复程序。
训练环境必须把允许修改的代码、禁止修改的验收文件以及最终验证运行分开。

网页任务同样如此：创建一条近似名称的假记录可能让宽松字符串检查通过。
验证器应检查目标对象身份、字段、权限和环境状态；当验证器无法观察最终状态时，应记作未判定而非成功。
模型自评可生成“哪一步可能失败”的解释，不能替代环境验收。

密集奖励能缩短学习等待，但任意过程分数可能改变目标。
例如奖励“每次执行测试”会鼓励无效重复；奖励“输出反思”会鼓励长文本。
在满足相应 MDP 假设时，势函数塑形 $r'_t=r_t+\gamma\Phi(s_{t+1})-\Phi(s_t)$ 可保持最优策略性质；隐藏状态不可用时，不能直接假定这一定理适用于自评历史分数。
实际方案需要用最终任务成功和过程指标一起检验。

## 11.5 一个动作对应哪些 token

训练日志至少需要 task ID、policy version、每次观测、模型动作、工具结果、奖励来源、终止原因。
对被拼接成训练序列的轨迹，再记录哪些区间是策略生成的。
系统提示、用户任务、环境观测和工具结果的策略损失掩码应为零。
动作文本的掩码为一；若训练包含模型内部生成的计划文本，则须明确该文本也属于策略采样、以及如何把它与可执行动作关联。

设有效动作 token 集为 $\mathcal M_i$，其序列 log-prob 为：

$$
\log\pi_\theta(a_i\mid h_i)=\sum_{u\in\mathcal M_i}\log p_\theta(x_u\mid x_{<u}).
$$

用 token 平均还是序列求和会改变长短动作的权重。
PPO 的比率是所选随机变量的概率比，不能把“序列概率比”和“逐 token 裁剪”悄悄混为同一个算法。
对长动作，序列概率比可能方差很大；实用实现常采取逐 token 目标，报告中应写出具体形式。
本仓库 [alignment.py](../src/fm_tutorial/alignment.py) 演示完成区间掩码和损失部件，未包含环境采样、策略版本管理或完整 Agent PPO 训练器。

## 11.6 采样和训练为何常常解耦

浏览器、命令行和模拟器的每条轨迹耗时不同，最长轨迹会拖慢同步批次。
异步采样提高设备利用率，但训练时收到的轨迹可能来自旧策略。
记录行为策略 log-prob 和版本号后，才能讨论重要性校正及策略滞后限制。
只把所有成功轨迹反复 SFT 是有用的筛选模仿学习，却不能因此声称执行了 on-policy RL。

重置失败、依赖下载失败和工具超时还会污染奖励。
应分别统计环境故障与策略失败，保存原始日志，让异常排除规则在看结果前冻结。
对于会产生副作用的工具，重试需要幂等操作或事务标识；否则“同一个动作重试三次”会改变任务本身。

## 11.7 本地可以验证什么

[agent.py](../src/fm_tutorial/agent.py) 暴露 `run_agent(policy, tools, verifier, *, max_steps=8, time_budget_seconds=30.0, self_judge=None, log_path=None)`。
策略和工具由调用者提供，执行器负责有界循环、日志和终止；返回 `status`、`answer`、`trace`、`steps`。
`verifier(answer, history)` 决定成功，`self_judge` 仅记录辅助判断。
错误动作、不存在的工具和工具错误都会消耗动作预算，避免无限“修复”循环。
时间预算是合作式检查：回调前后检查截止时间，不能中断一个永久阻塞的 Python callable。
真实部署仍需进程隔离、工具自身超时、权限控制和环境重置。

可先运行 `python -m unittest discover -s tests` 验证终止与日志行为。
这些小输入回归检查证明程序约定，不提供长程任务能力、公开基准成功率或训练收益的证据。
公开任务的采样和实际奖励测量按 [作业 05](../assignments/05-agent.md) 单独进行。

## 11.8 阅读与推导练习

1. 画出代码修复任务中“模型生成”“环境提供”“最终验证”的三个边界，标出每段 token 是否进入策略损失。
2. 对两条同任务轨迹写出终端回报和每步回报；说明为什么额外奖励“反思长度”可能损害目标。
3. 设组内奖励全部为零，解释增加 $\epsilon$ 为什么只解决数值问题，不能解决探索问题。
4. 用一次工具失败日志判断它应算模型错误、环境错误还是两者都需保留的事件。

源码进阶可阅读 [NeMo RL README](https://github.com/NVIDIA-NeMo/RL/blob/main/README.md) 与已核验的 [grpo_math_1B.yaml](https://github.com/NVIDIA-NeMo/RL/blob/main/examples/configs/grpo_math_1B.yaml)，观察采样、推理服务与训练后端的分工。
