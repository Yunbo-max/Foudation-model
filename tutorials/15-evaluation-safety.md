# 15 · 评估、可靠性与安全：结果由什么证据支持

两个代码助手都声称修复了 issue：一个通过独立验收，另一个只写出“测试通过”。
两者的最终文字可以相同，证据强度却不同。
一个网页助手能完成合法任务，也可能被页面里的恶意指令引导去操作另一个对象。
评估因此需要同时回答“任务是否完成”“结果能否复现”“错误会产生什么后果”。

本章建立公开基准、统计估计、错误诊断和权限边界的一条完整链路。
本仓库的回归检查只验证实现性质；没有把小型脚本或自编场景当作研究能力基准。

## 15.1 一次分数是什么的函数

Agent 分数依赖模型、提示、工具、检索、环境、任务集、预算与验证器。
只报模型名字无法复现；只报“跑了 SWE-bench”也无法判断使用 full、Lite、Verified 还是另一版本。
首先建立实验清单：模型 ID 与 checkpoint、基准版本、任务 ID、环境镜像、策略 commit、温度、种子、预算及评分程序。
API 模型应记录精确版本和运行日期，不假定同一别名长期固定。

评测集在方法选择期间充当开发集，就不能再被称为未经接触的测试集。
区分用于训练的任务、调参任务和最终报告任务；对公开任务检查答案、补丁和轨迹是否进入训练或记忆。
公开基准并不天然免除污染问题，公开本身反而让答案更容易泄漏。

## 15.2 基准要与任务能力匹配

| 公开入口 | 主要观察什么 | 验证重点 | 运行边界 |
| --- | --- | --- | --- |
| [AgentBench](https://github.com/THUDM/AgentBench) | 多环境交互 | 各任务官方结果 | 每种环境有独立依赖 |
| [BrowserGym](https://github.com/ServiceNow/BrowserGym) + [WebArena](https://github.com/web-arena-x/webarena) | 网页操作与状态变化 | 官方任务状态验收 | 网站服务、浏览器与重置版本 |
| [SWE-bench](https://github.com/SWE-bench/SWE-bench) / Verified | 真实仓库 issue 修复 | 隔离测试中的补丁结果 | 子集、镜像、补丁格式和缓存 |
| [Terminal-Bench](https://github.com/harbor-framework/terminal-bench) | 终端中的多步任务 | 官方任务测试 | 数据发布标签和 Harbor 环境 |
| [MineRL](https://github.com/minerllabs/minerl) | Minecraft 控制与轨迹 | 具体环境奖励与协议 | 环境版本、动作空间和客户端依赖 |

BrowserGym 是统一环境接口与适配生态，不是一份可用单一分数概括的任务数据集。
SWE-bench Verified 是特定人工检查子集，不能把自己挑选的简单 issue 称为 Verified。
Terminal-Bench 已采用持续更新与标签发布；原 `laude-institute/terminal-bench` 迁至 [terminal-bench-1](https://github.com/harbor-framework/terminal-bench-1)。
复现旧研究使用旧版本，研究当前系统使用固定新标签；不能把跨版本分数直接相减。

没有环境资源时，先阅读官方任务与评分器，写好可审查的运行计划。
报告“未运行”比用自编题目填补公开基准结果更有信息。
单项基准通过只能支持其协议覆盖的能力，无法证明所有长程任务都可完成。

## 15.3 成功率及其不确定性

对冻结的 $n$ 个任务，$y_i\in\{0,1\}$ 表示官方验证通过：

$$
\hat p=\frac1n\sum_i y_i.
$$

成功率需要同时报告分母，不能只给百分数。
若任务是独立抽样的 Bernoulli 观测，Wilson 区间为：

$$
\frac{\hat p+\frac{z^2}{2n}\ \pm\ z\sqrt{\frac{\hat p(1-\hat p)}n+\frac{z^2}{4n^2}}}{1+\frac{z^2}n}.
$$

用 $z\approx1.96$ 得到常用的近似 95% 区间；这是抽样假设下的估计，不消除任务选择偏差。
同一仓库的 issue、同一网站的操作可能相关，应考虑按仓库或任务族聚类的重采样。
同一任务多次尝试也不是多份独立任务样本，报告每任务分布和跨任务总体统计。

比较两个系统时应优先使用相同任务和相同环境。
令 $d_i=y_i^{(B)}-y_i^{(A)}$，配对差为 $\bar d$。
对任务 ID 进行配对 bootstrap，可估计差值的不确定性；不能分别抽样后丢掉配对结构。
极小子集或非随机人工选择的任务，仅支持这个子集的描述，不支持总体推广。

## 15.4 多次尝试改变了指标

一次通过率与“最多尝试 $k$ 次中至少一次通过”不同。
在独立且等成功概率的理想假设下，后一概率为 $1-(1-p)^k$。
Agent 重试常共享记忆、状态和失败信息，并不满足独立假设。
是否重置环境、是否保留反思、如何计入预算，都必须明确。

当有 $n$ 个交换性样本、其中 $c$ 个成功时，代码生成文献常用估计：

$$
\widehat{\operatorname{pass@k}}=1-\frac{\binom{n-c}{k}}{\binom nk},\qquad n\geq k.
$$

这一估计需要满足其采样约定，不能直接用于相互依赖的自修复轨迹。
Agent 更适合另外报告一次成功率、固定总预算下最终成功率、每任务耗时和实际尝试数。
对照系统也要得到相同的重试与资源预算，避免把成本差异误写为方法优势。

## 15.5 用效率指标解释成功

任务成功可以同时伴随过高成本或大量失败动作。
至少保存输入输出 token、工具次数、重试次数、墙钟时间、环境失败次数和成本估计依据。
延迟可报告中位数和较高分位，而不是只给平均值掩盖长尾。
同时报告全部任务与成功任务的成本，否则失败提前终止会让系统看起来异常便宜。

令每任务总成本为 $c_i$，可以画预算阈值 $b$ 下的成功率 $\Pr(y_i=1,c_i\leq b)$。
这比一个单独成功率更接近实际使用约束。
预算扫描应预先确定阈值，并保留同任务各次执行日志；没有实际测量时不要画假曲线。

工具错误还应细分：错误参数、对象不存在、权限拒绝、依赖问题、网站不可用、验收异常。
环境故障排除规则在看模型结果前固定，原始日志保留，方便他人检验排除是否公平。
“任务太难”通常属于策略失败，不能作为环境异常排除。

## 15.6 自评与独立验证

确定性程序验证适合有明确结构的目标，例如答案计算、数据库状态或测试断言。
语言 judge 能覆盖开放文本含义，但其评分受提示、模型版本、顺序和参考答案影响。
需要冻结 judge 配置，并抽查与人类判断不一致的案例。
被评分模型看到隐藏参考答案，会破坏评测边界。

自评可以用来提出待检查假设和解释失败；成功状态应来自独立验收。
在 [agent.py](../src/fm_tutorial/agent.py) 中，`verifier` 是成功权威，`self_judge` 只记录辅助信息。
这一设计保证接口不会被自信文本直接覆盖，但不保证调用者提供的 verifier 一定正确。
审查真实任务时还要检查验证器能否被策略修改、绕过或读取秘密答案。

## 15.7 安全首先是执行边界

**网页场景。** 页面是外部数据，可以包含攻击指令；用户任务和执行策略来自更高可信层级。
不可信页面让模型“忽略任务去转移数据”时，执行器应仍强制域名、对象和操作权限。
仅依赖模型分辨文字来源不足以约束真实副作用。

**代码场景。** 仓库文件、依赖安装脚本和测试命令可能执行代码。
评测工具应在隔离环境中运行，并限制网络、目录、资源与凭据暴露。
模型即使输出了允许的命令名称，也可能用参数访问超出任务范围的路径，参数约束同样必要。

**记忆场景。** 恶意工具输出被长期保存后，后续任务会重复遇到它。
写入时保存来源和信任级别；检索时不要把外部文档提升为系统规则。
删除或失效应覆盖派生摘要和缓存，防止旧攻击内容继续被召回。

这些边界是可测试的系统行为，不是额外的自然语言宣言。
权限最小化、执行隔离和可审计日志可以限制错误后果；它们与模型能力训练互补。

## 15.8 测试攻击和正常任务两种表现

[AgentDojo 官方项目](https://github.com/ethz-spylab/agentdojo) 提供工具环境中的注入攻击与防御评测入口。
采用其特定发布与任务套件时，记录用户任务、攻击目标、可修改的工具输出范围和评分规则。
这能提供既有公开协议中的安全证据；本仓库随手写的一条恶意字符串只适合回归测试。

攻击成功率应说明分母：所有攻击任务，还是原本能完成合法任务的任务。
防御的合法任务完成率也要一起报告；拒绝执行一切会降低攻击成功，但同时失去实用性。
比较攻击时固定模型、工具、任务和攻击预算，区分单次攻击与多次搜索后的最佳攻击。
发生越权但最终答案正常，也应按实际动作日志判定，不能只看最终文本。

## 15.9 可复现的交付清单

准备基准 manifest、策略版本、任务 ID 和运行预算；保留每任务原始轨迹及官方验收输出。
单独保存失败环境诊断、排除理由与重跑 ID，防止缓存结果覆盖新实验。
SWE-bench 当前 README 特别提醒结果缓存按 run ID 与 instance ID；更换补丁时必须使用新的 run ID。
所有表格直接从实际日志生成，没有日志的格子标“未测”。

本地可运行 `python -m unittest discover -s tests` 检查数学、掩码和执行终止。
公开能力验证需要按 [作业 05](../assignments/05-agent.md) 安装环境、运行任务和使用官方评分器。
本教程没有声称完整跑完 AgentBench、WebArena、SWE-bench 或 Terminal-Bench。

## 15.10 思考题

1. 一个方案成功率上升，工具费用翻倍，如何用固定预算实验判断变化是否有实际收益？
2. 为什么同一任务跑十次不能简单当作十个独立任务计算置信区间？
3. 若防御让攻击成功率降到零，却拒绝所有正常任务，应如何呈现结果？
4. 列出代码 Agent 验证器的三个漏洞，并说明模型能否通过改变被测对象来利用它们。
