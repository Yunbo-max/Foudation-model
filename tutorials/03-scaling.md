# 03　训练动力学与 Scaling：把“模型越大越好”变成可检验的问题

> 前置：[02 架构](02-architecture.md)；实现：[train.py](../scripts/train.py)、[scaling.py](../src/fm_tutorial/scaling.py)。

## 3.1 场景一：只有固定 GPU 时间，怎样分配模型与数据

你能使用一块 GPU 两天，有两个方案：训练更大模型但少读一些文本，或训练更小模型但读更多文本。
这不是仅比较参数量的问题，而是同一计算预算下模型容量与优化进展的配置问题。
Scaling law 试图用一组真实训练结果描述这个关系，再预测一个有限的邻近范围。
它不是训练之前即可套用的万能常数，也不是一次小模型拟合就证明“扩到万亿参数一定成功”。

先区分三个对象：训练损失曲线描述一个模型随优化过程的变化；规模曲线比较多个模型；计算最优前沿从给定预算下的候选中选择最好配置。
只测一个模型多个 checkpoint，不能独立识别模型规模的影响。
只测多个模型同样步数，也不意味着它们具有相同数据或计算预算。

## 3.2 从梯度到损失曲线：为何初始阶段很不一样

训练初期随机模型的词表分布可能接近均匀，平均交叉熵常在与 $\log V$ 同量级的区域。
真实初始化、权重共享和 logits 尺度会改变数值，因此 $\log V$ 是直觉基线，不是应强制达到的断言。
模型先学到常见 token、局部搭配与文体规律，复杂依赖可能需要更长训练。
一条快速下降曲线说明容易预测的信息正被拟合，不能据此宣称推理能力已经出现。

学习率 warmup 逐渐增加步长，常用来缓解训练初期优化状态与激活尺度尚未稳定的问题。
后期衰减使更新更小，但衰减过早也可能浪费数据。
余弦 schedule 的示意为：

$$
\eta(s)=\eta_{\min}+\frac12(\eta_{\max}-\eta_{\min})
\left[1+\cos\left(\pi\frac{s-s_w}{S-s_w}\right)\right],\quad s\ge s_w.
$$

$s_w$ 是 warmup 步数，$S$ 是计划总更新数；warmup 段需另行定义。
若中途把 $S$ 改大，当前与未来学习率可能全部改变，所以“续训更多步”不只是增加数据。
比较训练时记录 schedule 参数与实际学习率，而不只记录名称。
本仓库实际 schedule 以 [train.py](../scripts/train.py) 为准，公式用于解释常见选择，不声称全部都已实现。

## 3.3 训练 token 数与更新步数不是一回事

无 padding、每条长度 $T$ 的序列使用内部移位时，每批最多有 $B(T-1)$ 个 next-token 目标。
若累积 $A$ 个 microbatch，理想每次更新目标数为 $AB(T-1)$。
有 PAD 时应直接计数 mask 有效位置；稀疏 completion 训练又是另一种计数。
报告中区分“送入模型的 token”“有效损失目标 token”“独特语料 token”和“重复读取次数”。

一个被循环读十次的数据集，消费 token 数会增加十倍，但独特信息并未随之十倍增长。
重复数据可能仍有优化收益，也可能导致过拟合，需以固定独立验证结果判断。
把 epoch 当成跨数据集通用预算会误导：不同数据集一轮包含的文本量不同。
本项目 checkpoint 的 tokens 计数口径应在日志与报告中解释，并与 loss mask 核对。

## 3.4 计算估算 $C\approx6ND$ 从哪里来

对于以密集矩阵乘为主的 decoder 模型，单个参数在一次前向中通常贡献一次乘加，按两次 FLOPs 计。
反向对输入与权重各有相近矩阵计算，总训练成本粗略为前向的三倍。
因此常见近似：

$$
C\approx 6ND.
$$

$N$ 为参与主要密集运算的参数数，$D$ 为训练消费 token 数，$C$ 单位为 FLOPs。
乘加算两个 FLOPs 是这里的计数约定，需保持一致。
这个估算省略注意力随 context 的二次项、嵌入/词表头的细节、重算、通信和非矩阵操作。
长上下文、大词表、MoE 激活参数与总参数差异都会让误差变大。
实际训练时间还取决于硬件利用率，不能把 FLOPs 估算直接当成墙钟时间。

若设备标称峰值为 $F_{\mathrm{peak}}$ FLOPs/s，运行 $t$ 秒，估算 MFU 可写为 $C/(tF_{\mathrm{peak}})$。
必须注明使用的 dtype 峰值、计数方式与是否包含重算；不同口径下数字不能直接比较。
没有实际 $t$，只能做预算，不是测量。

## 3.5 幂律模型：描述可预测性，不能消除误差

一个常见模型为：

$$
L(N,D)=E+aN^{-\alpha}+bD^{-\beta},\quad a,b,\alpha,\beta>0.
$$

$L$ 是固定验证分布上的 NLL，$E$ 是拟合中的不可约项，后两项分别描述容量与数据不足。
若 $N,D$ 用原始计数，$a,b$ 的数值依赖单位；把参数单位换成百万时必须一起变换系数。
这个 $E$ 是拟合参数，不是已知的自然语言真实熵，也不证明模型最终能够达到它。
幂律是一种待验证假设，观测范围内的残差、外推表现与替代模型都应检查。

取对数可以方便分析 $L-E=aN^{-\alpha}$ 的斜率，但 $E$ 未知时不能直接用 $\log L$ 拟合成同一模型。
若 $L\le E$，对数残差无定义，暴露参数或拟合过程不合理。
非线性拟合对初值、边界与权重敏感；几乎重叠的候选参数可能给出相近训练误差，却给出不同远期预测。

## 3.6 固定预算下的最优分配：一步步推导

采用 $C=6ND$，固定 $C$ 后 $D=C/(6N)$。
代入损失：

$$
L(N)=E+aN^{-\alpha}+b(6N/C)^\beta.
$$

第一项随 $N$ 变大而下降，第二项因为数据预算减少而上升。
对 $N$ 求导并令其为零：

$$
-\alpha aN^{-\alpha-1}+\beta b(6/C)^\beta N^{\beta-1}=0.
$$

整理得到：

$$
N_*^{\alpha+\beta}=\frac{\alpha a}{\beta b}(C/6)^\beta,
\quad N_*\propto C^{\beta/(\alpha+\beta)},
\quad D_*\propto C^{\alpha/(\alpha+\beta)}.
$$

若 $\alpha\approx\beta$，两个最优量近似随预算平方根增长。
这解释 Chinchilla 类型结论的形式，而非声明你的数据也具有论文同样的指数。
若硬件可用模型尺寸、数据质量和训练稳定性限制候选，数学最优点可能不可实现。
服务成本也没进入该目标，所以计算最优预训练模型未必是整体生命周期最便宜的模型。

## 3.7 场景二：四个点拟合五个参数，看起来极好却不可信

假设所有实验都读取相同数据量 $D_0$，变化的只有 $N$。
那么 $E+bD_0^{-\beta}$ 在这些观测中只表现为一个常数。
无论样本有多少，都不能仅从这组 iso-data 数据分别识别 $E,b,\beta$。
正确的简化是 $L(N)=E'+aN^{-\alpha}$，并把 $E'$ 的条件写清。
少量点也不能稳健识别这个三参数模型；应控制参数边界、保留预测点并报告不确定性。

若要研究 $N,D$ 的交互，需让它们在实验设计里独立变化。
例如三种宽度、三种 token 预算，形成一个二维网格；这只是实验设计建议，实际成本先估算。
如果只有一组预算，宁可报告测量曲线与局部趋势，也不要输出缺乏识别基础的五参数“定律”。
本仓库 [scaling.py](../src/fm_tutorial/scaling.py) 实际只拟合更简单的局部描述：$\log L=a+b\log x$，即 $L=e^a x^b$。
它没有不可约损失 $E$，不拟合完整 Chinchilla 形式，也不能建立计算最优分配；前面的推导属于学习与外部扩展。
接口只消费真实测量，强制另一轴固定并保留 hold-out，科学解释仍需由实验设计保证。

## 3.8 Iso-data、iso-FLOPs 与 iso-time 分别回答什么

| 设计 | 固定的量 | 能回答的问题 | 常见混杂 |
| --- | --- | --- | --- |
| iso-data | 消费 token 数 | 相同训练文本量下容量效果 | FLOPs 不同、优化不同 |
| iso-FLOPs | 估算/实测计算预算 | 计算最优分配 | 近似计算误差、学习率 |
| iso-time | 同类设备墙钟时间 | 实际预算内可得效果 | 吞吐与实现质量 |
| fixed validation | 验证文档与口径 | 损失可比较 | tokenizer、边界处理 |

固定步数只在 batch、context、累积和 mask 一致时才近似固定 token 数。
硬件不同的 iso-time 比较同时研究了系统，不能解释成纯模型 scaling。
统计误差与系统波动也不同：前者来自训练/评估样本，后者来自设备运行，应分别记录。

## 3.9 场景三：扩到 100M 前先用 pilot 发现预算错误

先在真实 TinyStories 或 WikiText 上跑几个小模型，测每步时间、有效 tokens/s、显存、稳定性和固定验证 NLL。
[cpu.json](../configs/cpu.json) 是开发配置，[100m.json](../configs/100m.json) 是约 0.1B 的 GPU 起点；不是只改一个参数就得到同样实验。
参数数使用实际模型计数，预算计算使用实际 token 数，日志保存完整配置。
本书没有已经跑完的 100M 预训练结果，不能把教学配置文件当成模型能力证据。

从 pilot 到大规模时，先检验学习率范围、context 与 batch 可行性，再决定完整训练时间。
一个短 pilot 可能仍处在快速学习阶段，长时间曲线不应按初始斜率线性外推。
把一个稍大的模型留作真正预测目标，比随机删掉一个与训练点几乎相同的重复测量更能检验外推。
查看真实值与预测值后再选择模型，会污染这个 hold-out；要预先固定它。

## 3.10 真实实验记录与拟合协议

训练记录至少包括：`run_id`、实际 $N$、消费 $D$、数据/tokenizer 版本、seed、验证 NLL、墙钟时间、硬件和估算 FLOPs。
CSV 必须包含 `params,tokens,loss`，可附 `split=train|holdout`；三个不同训练轴值加至少一个 hold-out 是最低输入条件。
缺少显式 split 时脚本保留最大轴值的约 20% 为外推检查；正式研究应在看结果前明确写好划分。
固定 `tokens` 可拟合 `params` 轴，固定 `params` 可拟合 `tokens` 轴：

```bash
python scripts/fit_scaling.py --csv measurements.csv --axis params --output runs/scaling-fit.json
```

`measurements.csv` 应由实际日志汇总，不是仓库内置数据；具体契约见 [fit_scaling.py](../scripts/fit_scaling.py)。
不把预设公式生成的 loss 当作测量，也不把单元测试中的数值数组当作研究结果。
没有运行的数据点在计划表中保留预算，在测量表中省略或显式标记未运行。

拟合时先画原始数据，再对比简单基线，例如固定值或局部线性关系。
固定训练/hold-out 划分，用训练点估计参数，在 hold-out 计算绝对误差与相对误差。
相对误差 $|\hat L-L|/L$ 说明预测量的偏差；不代表模型质量提升百分比。
脚本返回 log-space RMSE 与逐 hold-out 预测，若报告相对误差需自己从真实值与预测值计算，不混称两个指标。
按 run 重采样或重复训练可以给出不确定性线索，但少量 seeds 的置信区间不能保证覆盖未来规模。
拟合不稳定、指数碰边界、hold-out 误差大都应写进报告，而不是只展示最漂亮曲线。

## 3.11 常见误判

- 训练损失降而验证损失升：先检查过拟合与分布，不先宣布“新能力”。
- 大模型更差：可能是优化不足、学习率未调、数据太少或实现错误，需要逐项证据。
- 某 benchmark 分数跳变：先检查离散评分阈值、样本数量和输出格式，再讨论能力变化。
- 以小模型拟合数据比例后推广到全部领域：数据质量、混合配方和 tokenizer 已经变化。
- 把论文中的 tokens/parameter 经验值当硬性训练标准：论文针对特定模型、数据、目标与预算。

## 3.12 检查理解

1. 同样 1000 步，context 翻倍而 batch 减半，输入 token 与监督 token 是否完全相同？
2. 推导 $N_*,D_*$ 的预算指数，并解释 $\alpha\ne\beta$ 时的变化。
3. 为什么 iso-data 数据不能识别完整的 $E,a,b,\alpha,\beta$？
4. 为一个真实语料设计至少一个预测点，列出在看结果前必须固定的选择。
5. 训练算力固定与整个服务生命周期成本固定，会选择同一个模型吗？给出一个反例机制。
